# Block backend qualification

The raw block reference adapter accepts the exact profiles in
[its reference](../reference/topics/block-profiles.md) for education, historical
data and interoperability tests. This acceptance does not qualify these
backends for production encryption or claim an independent cryptographic audit.
AES retains its separate backend and API.

## Pinned dependencies

| Crate | Exact version | Features | Declared MSRV |
| --- | --- | --- | --- |
| `des` | 0.9.0 | `zeroize` | Rust 1.85 |
| `blowfish` | 0.10.0 | `zeroize`; no `bcrypt` | Rust 1.85 |
| `idea` | 0.6.0 | `zeroize` | Rust 1.85 |
| `rc2` | 0.9.0 | `zeroize` | Rust 1.85 |

All four are maintained in
[RustCrypto/block-ciphers at 9a84f2f](https://github.com/RustCrypto/block-ciphers/tree/9a84f2f8b581f62bcd00e16b5e11a2f6251916ee)
under MIT OR Apache-2.0. They are pure Rust, `no_std`, forbid unsafe code and
require no C library, system crypto service or runtime CPU feature. The lockfile
records registry checksums. The shared `cipher` 0.5 API supplies block traits;
Cube owns profile validation, not primitive algorithms.

The upstream project explicitly states that its non-AES ciphers have not
received formal security review and are not constant-time implementations.
DES/Blowfish/RC2 use secret-dependent lookups; IDEA also has data-dependent
arithmetic and inverse computation. Passing known answers does not establish
side-channel safety. There is no hardware/software timing certification or
secure message-encryption claim.

The RustSec tree
[`965bf9a`](https://github.com/RustSec/advisory-db/tree/965bf9ad083b58e6340d65829d85217b18be9290)
was checked on 2026-11-04 and contains no crate-specific advisory directory for
these four packages. This is a dated source inspection, not `cargo audit` or
proof of no vulnerabilities. DES and Triple DES remain obsolete regardless of
that observation. No patent-clearance opinion is inferred from software licences.

## Profile and secret review

Core accepts only reviewed full-round identifiers. DES parity is ignored by the
backend; weak/degenerate keys remain accepted solely for forensic compatibility.
Blowfish fixes big-endian external words and 4..56-byte keys. IDEA fixes its
original 128-bit key and 64-bit block. RC2 validates 1..128 key bytes and a
separately required 1..1024 effective bits before calling the backend's unchecked
effective-length constructor. No foreign profile settings are silently ignored.

Fixed-byte and parameter ceilings precede output allocation and key expansion.
Owned decoded keys and backend schedules use zeroization. Upstream temporary
key-expansion stacks are not uniformly wiped; parser, caller, interpreter,
compiler and OS copies are outside the guarantee. Debug/error paths redact key
material. Keys enter the CLI through bounded regular files and native SDKs
through memory. No modes, padding, defaults, RNG or public secret CLI arguments
are added. Private contract policy is inherited by Wasm and native Play.

## Verification sources

The checked-in
[reference vectors](../../crates/cube-core/src/ciphers/block_profiles/vectors.json)
are independent expected bytes, not outputs generated by Cube. They include
Botan's DES and multiblock IDEA material, LibTomCrypt/NESSIE two-key Triple DES,
Go's three-distinct-key Triple DES cases, the Blowfish author's big-endian and
variable-key answers, and all eight RFC 2268 RC2 vectors, including effective
lengths 63, 64, 128 and 129.

Core, CLI, native Python, actual Wasm and native Play execute that corpus in both
directions. Separate checks cover empty/repeated blocks, malformed keys/settings,
partial input, exact/one-over byte and parameter limits, canonical schemas,
private retention and forbidden capture. Generated TypeScript requires RC2's
effective length and refuses it on other profiles. Platform/browser CI remains
the evidence for those hosts; local execution alone does not prove them.
